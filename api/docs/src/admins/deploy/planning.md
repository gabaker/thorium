# Planning a Deployment

Read this page before installing Thorium on a cluster you intend to keep. It lists what the
Kubernetes cluster and your workstation need, how to size the deployment, which S3 store and
ingress to use, how to handle credentials and offline sites, and which version to deploy.

## Kubernetes cluster

- **A storage class** for the backing services' volumes: the cluster's default `StorageClass`,
  or set `infra.storageClass`. Set it before the first install; a volume's storage class can't
  change afterwards.
- **Kernel settings** on every node that runs Scylla or Elasticsearch:

  ```
  fs.aio-max-nr=2097152
  vm.max_map_count=262144
  ```

  Instead of setting `vm.max_map_count` on the nodes yourself, `infra.elastic.setMaxMapCount: true`
  sets it from a privileged init container on each Elasticsearch pod (the elastic namespace must
  allow privileged pods), and `infra.elastic.config` can set `node.store.allow_mmap: false`
  instead (slower searches, no kernel setting needed).
- **A CNI that enforces NetworkPolicy** (such as Calico or Cilium) when the chart deploys
  SeaweedFS: SeaweedFS's master and filer ports have no authentication, and the chart's
  `seaweedfs-ingress` policy only lets other pods reach its S3 port.
- **An ingress controller** to reach Thorium from outside the cluster. The chart renders an
  nginx `Ingress` or a Traefik `IngressRoute` (see [Ingress](./helm-configuration.md#ingress));
  without one, use `kubectl port-forward`.
- **Pod Security**: Scylla's core dump volume is a `hostPath` (turn it off with
  `infra.scylla.coredumps.enabled: false` in namespaces that enforce the `baseline` or
  `restricted` level), node provision pods mount host paths as root, and the k8s scaler runs
  job pods in its own namespaces. See [Pod security](./helm-configuration.md#pod-security).
- **One Thorium deployment per Kubernetes cluster** (see
  [Deployment Concepts](./concepts.md#one-deployment-per-kubernetes-cluster)).

## Tools

- `kubectl` with a kube config for the cluster.
- Helm 3.8 or newer, for OCI charts. minithor downloads its own pinned Helm when none is on the
  `PATH`.
- `jq`, only for [converting a pre-Helm deployment](./convert-to-helm.md).

## Sizing

The chart defaults are sized for a single-node development cluster: one Scylla node in developer
mode (which skips Scylla's hardware checks), one Elasticsearch node, SeaweedFS, one API replica,
and no CPU or memory limits on the Thorium components.

The thorium chart ships `values-production.yaml`, a starting point for multi-node clusters: three
Scylla nodes in production mode, three Elasticsearch nodes, three Postgres replicas, three API
replicas, an external replicated S3 store instead of SeaweedFS, and a Traefik ingress with TLS.
`helm show values` only prints the umbrella chart's own values, so pull the chart to read it and
the subcharts' values:

```bash
helm pull oci://ghcr.io/cisagov/thorium/charts/thorium --version $VERSION --untar
less thorium/values-production.yaml thorium/charts/*/values.yaml
```

Scylla's production mode refuses to start on storage it doesn't support: give Scylla nodes XFS
on NVMe or SSD storage, and enough CPU and memory. Size volumes before the first install: Scylla's
and SeaweedFS's volume sizes are fixed afterwards, and the others can only grow with a storage
class that allows expansion.

The scaler keeps part of each worker node's CPU, memory, and storage free for things outside
Thorium (the `reserved_*` system settings, changed with
[`thoradm settings`](../thoradm/thoradm.md#system-settings)), so leave room for that when sizing
worker nodes.

## S3 store

| Store | Use it for | How |
|-------|------------|-----|
| SeaweedFS | Single-node and small deployments; a single process on one volume | Deployed by the thorium chart (`global.managed.s3: true`, the default) |
| Rook/Ceph object store | Replicated storage across nodes on bare metal or VMs | Installed by megathor, or by hand ([Rook](./install-rook.md)) |
| Any other S3-compatible service | Cloud object storage or an existing store | [External services](./helm-configuration.md#external-services) |

The operator creates Thorium's own buckets (or only checks them, with
`thorium.s3.skip_bucket_auto_create`). With tracing enabled, the bucket Quickwit stores traces in
(`quickwit` by default) is created by the chart only in its own SeaweedFS; create it yourself in
any other store.

## Tracing

`global.quickwit.enabled` (default `true`) deploys Quickwit, its Postgres metastore, the
`quickwit` bucket, and the Jaeger trace viewer, and points Thorium's traces at them. Turn it off
to run without them; Thorium then sends no external traces unless
`operator.backends.tracing.grpcEndpoint` names another OTLP gRPC collector.

## Credentials

Decide how credentials are managed before the first install:

- **Generated by the chart** (the default): every credential you don't set is generated once and
  kept in the `thorium-credentials` Secret. Back that Secret up; it can't be regenerated without
  locking out every user.
- **Supplied from your own secret store**: required for GitOps renderers (Argo CD, Flux) and
  `helm template`, which can't read existing Secrets. Every credential the deployment uses must
  then be set in the values.

See [Credentials](./helm-configuration.md#credentials) for the full rules.

## Offline sites

Every image the charts deploy can come from a mirror registry (`global.imageRegistry` on both
charts). The script `deploy/charts/scripts/list-images.sh` in the Thorium source repository prints
every image for the values you pass it, with its path in the mirror, and megathor's
`offline-stage.yml` stages the charts and image list for an offline megathor run. Tool images
referenced by a toolbox must be mirrored separately. See
[Offline installs](./deploy-helm.md#offline-installs).

## Choosing a version

Thorium release tags (`X.Y.Z`) publish the Thorium image and both charts under the same version,
and the `latest` image tag points at the highest release. The charts deploy the image of their
own version by default. Builds of the default branch publish prerelease charts versioned
`<version>-<branch>.<run number>.g<short sha>`, which deploy the image built from the same
commit; use them only for testing.

Plan for upgrades from the start: a newer Thorium may bring a new [revision](./concepts.md#revisions)
that waits for an admin to approve it (see [Upgrading Thorium](./upgrades.md)).
